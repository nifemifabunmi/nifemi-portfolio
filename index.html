Pharmaceutical document intelligence

TL;DR: I built a prototype that turns scanned supplier PDFs into something you can ask questions. It reads pages with OCR, splits files into documents, retrieves relevant passages, and answers in a chat window. I compared three OCR engines and three embedding models and measured the results.

Key points

  • Compared Tesseract, EasyOCR, and PaddleOCR on a scanned supplier PDF and recommended one for automation.
  • Extracted text and bounding boxes with PyMuPDF so layout was preserved.
  • Used a local LLM to find document boundaries and label each page in multi-document PDFs.
  • Tuned chunking and retrieval, then compared three embedding models and logged the differences.
  • Delivered a Gradio chatbot and a Colab demo reporting recall, MRR, and response metrics.

Skills used

PythonOCRPyMuPDFEmbeddingsRAGLocal LLMsGradioEvaluation (recall, MRR)

What I learned

  • Retrieval quality starts before retrieval: OCR errors and wrong page boundaries show up later as wrong answers.
  • Side-by-side comparisons with metrics gave me a reason for every tool choice instead of a guess.

What I wish I had done

  • Build a labeled set of test questions first, so every change could be scored the same way.
  • Test on more document types than a single supplier format.

What I'd do next

  • Show the source page for every answer so a reviewer can verify it quickly.
  • Add a confidence threshold that routes uncertain extractions to a human, which matters in a regulated industry.
  • Try hybrid search (keyword plus embeddings) and compare it on the same test set.
  • Estimate processing time and cost per document against manual review, so the value is stated in dollars and hours.

Backtesting engine

TL;DR: A Python backtester for a 20/50-day moving-average crossover with an RSI filter, plus a Streamlit app. Its main lesson was that a backtest can be quietly wrong: my first version skipped trades, and an independent vectorised calculation exposed it.

Key points

  • Whole-share sizing, a 0.1% fee per trade, and fills at the next bar's close rather than the signal bar.
  • Result on AAPL, about two years of daily data, $100,000 starting capital: +16.25% total return, 13 trades, -18.57% maximum drawdown.
  • Buy and hold over the same period: +42.09% with a -30.22% maximum drawdown.
  • Filling at the signal day's close instead would have shown +19.92%, which is why same-bar fills flatter results.
  • Single-asset backtest is verified. Multi-asset portfolio code (risk parity, mean-variance) is written but not yet verified.

Skills used

PythonPandasNumPyyfinanceStreamlitBacktestingDrawdown analysisCross-validation of results

What I learned

  • A backtest can be quietly wrong. My original code skipped a buy when the fee didn't fit in the leftover cash, and skipped the matching sell too. Two of seven buys never happened, which turned +19.9% into -15.0%.
  • Acting one bar after a signal, as a real trader must, cut the return from +19.92% to +16.25%.
  • Win rate alone misleads. Only 2 of 6 closed trades won, yet the strategy made money because the winners were much larger than the losers.
  • Drawdown is measured from the running peak, not from starting capital.

What I wish I had done

  • Write the independent cross-check before the main backtest instead of after.
  • Test on many tickers and periods from the start. One stock and 13 trades is too little to say anything about the strategy.
  • Validate the machine-learning experiments properly. Overlapping targets and filled missing values mean those accuracy figures can't be trusted, so I label that module experimental.

What I'd do next

  • Compute the Sharpe ratio the standard way (mean of daily excess returns) and add a beta and alpha regression against the benchmark.
  • Add a slippage model and fill at the next open instead of the next close.
  • Use walk-forward testing and run the strategy across many tickers and periods.
  • Report risk-adjusted metrics next to return. The strategy earned less than buy and hold but with a shallower drawdown, and a risk-adjusted view is the fair way to compare them.
  • Add unit tests for the indicators and metrics, and use Wilder-smoothed RSI.
  • Label the Real-Time tab as simulated or connect it to real data. Right now it shows generated numbers.

Interpretable music recommender

TL;DR: A small, testable recommender where every score can be traced. It retrieves candidates, scores them, ranks for diversity, and explains each pick. I evaluated it against baselines, and reported where improvements disappeared under proper validation.

Key points

  • Two-stage design: retrieval with a progressively relaxed genre and mood filter, then scoring with an artist-repeat penalty.
  • On seven hand-labelled listeners: 0.59 NDCG@5, against 0.11 random and 0.45 genre-only. The intervals overlap, so I call it an encouraging signal, not proof.
  • A search over 800 weight configurations reached 0.62 in-sample, but dropped to 0.56 vs 0.59 when each listener was held out. I kept the original weights.
  • On a 1,985-track catalog with synthetic listeners, no method won under both taste assumptions, and the README says so.
  • Optional AI-written explanations are accepted only if a local guardrail passes, otherwise the rule-based text is shown.

Skills used

PythonpytestStreamlitNDCG and precision@kAblation studiesLeave-one-out validationGitHub ActionsModel cards

What I learned

  • An improvement that only shows up in-sample is probably overfitting. Holding out a listener made that visible.
  • Simple, traceable scoring gave up some accuracy but made every result explainable, which is a real trade-off and not a free win.
  • Reviewing AI-generated changes matters. An AI review found real bugs in my code, including a diversity penalty applied after the top-k cut.

What I wish I had done

  • Collect real listener data. Seven labelled listeners and synthetic benchmarks limit how much I can claim.
  • Avoid mood labels derived from the same audio features used for scoring, since they aren't independent evidence.

What I'd do next

  • Gather consented listener taste files, which the repo already supports, and publish real-user results.
  • Extend diversity beyond artists to genres, to reduce the filter-bubble effect the model card describes.
  • Apply this validation discipline to the trading engine. Out-of-sample testing and overfitting checks are exactly what a quant interviewer looks for.
